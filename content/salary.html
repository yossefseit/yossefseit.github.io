Case study / Application delivery

Egypt Salary Calculator.

An Arabic-first React application that makes salary estimates easier to inspect, with 57 verified tests and static delivery configured for GitHub Pages.

01 / Problem

Make the calculation understandable.

Salary conversion is often presented as one unexplained number. This project exposes the implemented tax, insurance and deduction components in an Arabic right-to-left interface, with gross-to-net and net-to-gross modes and monthly or annual periods.

The delivery task is equally concrete: build the TypeScript application at its project path, run the sensitive calculations and interface checks, and publish only the resulting static bundle through GitHub Pages.

02 / Architecture

Local calculations. Static delivery. Optional enrichment.

Client

React + TypeScript

Vite builds for the /egypt-salary-calculator/ project path. A pure domain module calculates locally and uses bounded binary search for net-to-gross estimates.

Delivery

GitHub Pages artifact

The workflow runs the tests and build, uploads dist/, then uses Pages deployment permissions and a short-lived OIDC token. No Azure deployment credential is required.

Reference API

Optional and currently unhosted

The repository contains a .NET 10 Function for validated Frankfurter responses, but Pages cannot host it and the production build has no API base configured.

03 / Implementation

Keep policy rules apart from interface state.

The domain module contains progressive brackets, exemptions, insurance limits, period conversion and a documented rules effective date. The React layer handles validation, display, theme persistence and the optional exchange-rate state.

Delivery path

push to main
  → locked dependency install
  → tests → lint → production build
  → GitHub Pages artifact from dist/
  → deploy-pages with short-lived OIDC
  → /egypt-salary-calculator/

independent CI → tests + lint + build

The deployment job receives only pages: write and id-token: write. GitHub issues the short-lived deployment identity; the repository stores no cloud credential for Pages.

04 / Decisions & trade-offs

Accuracy needs explicit limits.

  • Pure calculation module: deterministic rules are easy to test and stay independent of the network, though law changes still require human review and updates.
  • Binary-search gross-up: a bounded search is simpler and safer across bracket boundaries than maintaining a fragile inverse for every rule combination.
  • Static Pages delivery: the calculator needs no application server for its core function, so Pages reduces the active cloud surface. It cannot run the repository's .NET Function.
  • Optional external rate: the Pages build deliberately has no API base until that service has a separately validated host. USD enrichment can fail without blocking EGP calculations.
  • Historical Azure path: the August 2026 App Service run remains useful deployment evidence, but it does not describe the current hosting target.
The calculator provides educational estimates. Actual payroll can differ because of allowances, bonuses, exemptions and regulatory changes.

07 / What I learned

Delivery evidence is stronger when failure states stay visible.

Separating the calculation from network calls made the application more resilient and the tests more meaningful. The pipeline reinforced the difference between a successful deployment event and ongoing service health. It also showed why infrastructure and rollback need first-class source control beside application delivery.
