Case study / Governance as code

Azure Governance Automation Lab.

An audit-first personal lab for expressing subscription policy, bounded access, cost notifications and lifecycle safety as reviewable Bicep and guarded scripts.

Status: Lab: CI validated; Azure deployment pendingRole: Governance design, IaC & testsScope: Personal lab
View code Pipeline evidence

01 / Problem

Build guardrails that can be reviewed before they write.

Subscription governance can change how every resource is evaluated. This lab makes the default posture deliberately conservative: audit first, keep access narrow, alert on cost signals and require an explicit path before policy can modify resources.

The second problem is lifecycle safety. Conditional resources, policy identities and incremental deployment can survive a parameter change, so deployment and cleanup have to share a deterministic inventory.

02 / Architecture

Policy, access, cost and protection in one baseline.

Policy baseline

Three definitions, one initiative

Required resource-group tags and allowed locations default to Audit. Inherited missing tags default to Disabled.

Cost notifications

Budget → action group

Actual and forecast thresholds provide signals. The example contains no receiver and a budget does not stop spending.

Protected control plane

Governance resource group

A CanNotDelete lock defaults on. Optional group Reader access defaults off.

03 / Implementation

One deployment manifest follows the whole lifecycle.

Subscription-scoped orchestration composes modules for policy, the action group, budget, resource-group lock and optional access. Experimental Bicep assertions guard important parameter combinations at compile time.

Bash and PowerShell paths perform context checks, local compilation, authenticated validation, what-if and exact confirmations. Cleanup reads the named deployment manifest, verifies IDs, scope and ownership, removes dependent resources in order and refuses unexpected inventory.

04 / Decisions & trade-offs

Enforcement follows evidence.

  • Audit-first defaults: the baseline observes drift before enforcing or changing resources. Stronger effects require a conscious parameter change.
  • Remediation is separate: enabling Modify creates the identity and role assignment; existing resources are not changed until remediation is explicitly requested.
  • Budget alerts are signals: actual and forecast notifications support action but cannot guarantee a spending ceiling.
  • Conditional identity lifecycle: toggling away from Modify can retain deterministic role assignments under incremental deployment. Full guarded cleanup is required before switching states.
  • Experimental assertions: stronger compile-time guards currently require Bicep language version 2.1-experimental.

06 / Current status

Lab: CI validated; Azure deployment pending.

The modules, lifecycle scripts, failure guards and runbooks are authored. The next milestone is a bounded, authorized lab run with sanitized evidence for validation, what-if, deployed controls, evaluation behavior, optional remediation, notifications and complete teardown.

07 / What I learned

Configuration flags create lifecycle commitments.

A disabled condition does not necessarily remove what an earlier incremental deployment created. Policy Modify connects effect, identity, role assignment and remediation. Treating cleanup evidence as part of the design made those state transitions visible before a subscription was involved.
