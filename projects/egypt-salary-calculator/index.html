Case study / Application delivery

Egypt Salary Calculator.

An Arabic-first React application that makes salary estimates easier to inspect, supported by tested delivery to Azure App Service through GitHub Actions and federated identity.

Status: 57 tests passing; deployment recordedRole: Design, application & deliveryReviewed: 8 Sep 2026
View code Deployment evidence

01 / Problem

Make the calculation understandable.

Salary conversion is often presented as one unexplained number. This project exposes the implemented tax, insurance and deduction components in an Arabic right-to-left interface, with gross-to-net and net-to-gross modes and monthly or annual periods.

The work also created a concrete delivery problem: build a small TypeScript application, test its most sensitive boundaries, and release static assets to Linux App Service without a stored Azure client secret.

02 / Architecture

Local calculations. Separate delivery and reference data.

Client

React + TypeScript

Vite builds the Arabic RTL interface. A pure domain module calculates locally and uses bounded binary search for net-to-gross estimates.

Delivery

GitHub OIDC

The deployment workflow builds and tests, publishes an artifact, requests a short-lived identity token, signs into Azure and deploys to Linux App Service.

Reference API

Optional .NET Function

A separate .NET 10 isolated function validates Frankfurter responses and applies a five-second upstream timeout. No Function deployment workflow is committed.

03 / Implementation

Keep policy rules apart from interface state.

The domain module contains progressive brackets, exemptions, insurance limits, period conversion and a documented rules effective date. The React layer handles validation, display, theme persistence and the optional exchange-rate state.

Delivery path

push to main
  → locked dependency install
  → production build + tests
  → immutable workflow artifact
  → GitHub OIDC / managed identity
  → Azure App Service for Linux

independent CI → tests + lint + build

The workflow uses id-token: write and identity, tenant and subscription identifiers with azure/login. It does not store an Azure client secret in the repository.

04 / Decisions & trade-offs

Accuracy needs explicit limits.

  • Pure calculation module: deterministic rules are easy to test and stay independent of the network, though law changes still require human review and updates.
  • Binary-search gross-up: a bounded search is simpler and safer across bracket boundaries than maintaining a fragile inverse for every rule combination.
  • Optional external rate: a failure does not block EGP calculations. The Function adds deployment and availability work that is not yet automated in the repository.
  • App Service delivery: it demonstrates the Azure pipeline clearly. The infrastructure was configured through Portal/CLI and is not yet reproducible Bicep.
The calculator provides educational estimates. Actual payroll can differ because of allowances, bonuses, exemptions and regulatory changes.

06 / Current status

Application source ready; cloud lifecycle still partial.

The React application, 57-test suite, CI and App Service workflow are present and pass locally. Historical delivery evidence is public. Reproducible cloud infrastructure, Function deployment automation, independent payroll-rule review and current demo availability remain open.

07 / What I learned

Delivery evidence is stronger when failure states stay visible.

Separating the calculation from network calls made the application more resilient and the tests more meaningful. The pipeline reinforced the difference between a successful deployment event and ongoing service health. It also showed why infrastructure and rollback need first-class source control beside application delivery.
